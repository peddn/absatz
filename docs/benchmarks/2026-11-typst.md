# Satz-Benchmark M0 – Typst 0.15.1 (16.11.2026)

Frage: Wie schnell setzt Typst ein generiertes 100-Seiten-Dokument neu – beim Tippen und nach einer Vorlagenänderung – nativ und im Browser?

## Aufbau

- **Dokument:** `absatz_core::sample::document(10)` – 10 Kapitel, 60 Abschnitte, ~500 Absätze mit Fußnoten, Listen, Hinweisen, Tabellen, Formeln, Zitaten, Inhaltsverzeichnis, Kopfzeile mit Kapitelname, Fußzeile „Seite x / y“. 102 Seiten A4.
- **Pipeline wie geplant:** Modell → `codegen::typst` → Typst (`Typesetter`) mit Vorlagensatz „standard“ (`tokens.json` + `template.typ`).
- **Messung:** `absatz_typeset::bench::run` – derselbe Code nativ (`just bench`) und im Web Worker (`just bench-web`).
  - Tippen: 30 Zeichen nacheinander in einen Absatz in der Dokumentmitte, jedes Mal ganze Pipeline.
  - Satz früh einfügen: Satz in Kapitel 1 → alle folgenden Zeilen und Seiten verschieben sich.
  - Vorlagenänderung: Grundschriftgröße bzw. Farbe von Überschrift 2, jeweils mit neuen Werten (kein Cache-Treffer).
- **Maschine:** Cloud-VM mit 2 Kernen, 7 GB RAM (eher langsam). Chrome for Testing 153, Wasm-Release-Build (LTO, `wasm-opt -O3`).

## Ergebnisse

### Chromium (Wasm im Web Worker, ein Thread)

Endstand M0: `comemo::evict(1)`, unveränderte Eingaben werden nicht neu gesetzt.

|---|---:|---:|---:|
| Typesetter anlegen (Schriften laden) | 27 ms | 22 ms | 22 ms |
| Codegenerierung (ganzes Dokument) | 2 ms | 4 ms | 8 ms |
| Kaltstart (erstes Setzen) | 1 138 ms | 2 520 ms | 4 176 ms |
| **Tippen: Median pro Zeichen** | **29 ms** | **72 ms** | **143 ms** |
| Tippen: Maximum | 72 ms | 142 ms | 238 ms |
| Satz früh einfügen (Median) | 57 ms | 77 ms | 161 ms |
| **Vorlage: Grundschriftgröße** | **499 ms** | **1 543 ms** | **3 240 ms** |
| Vorlage: Farbe Überschrift 2 | 536 ms | 1 720 ms | 3 324 ms |
| Eine Seite als SVG | 32 ms | 26 ms | 70 ms |
| Eine Seite als Raster (2 px/pt) | 77 ms | 53 ms | 91 ms |
| PDF-Export gesamt | 296 ms | 625 ms | 804 ms |
| Wasm-Speicher danach | 322 MB¹ | **292 MB** | 554 MB |

¹ Lauf mit `evict(10)`. Zum Vergleich 102 Seiten mit `evict(10)`: 947 MB Speicher, Tippen 70 ms, Vorlage 1 654 ms.

Fallstrick (gemessen): Mit `evict(1)` ist ein unveränderter Neusatz ein reiner Cache-Treffer; danach sind alle feinen Layout-Einträge verworfen und der nächste Tastendruck kostete 1 677 ms. Deshalb überspringt `Typesetter::compile` unveränderte Eingaben.

## Folgerungen

1. **Typst ist für die Vorschau schnell genug, für die Tipp-Latenz nicht.** 72 ms pro Zeichen bei 100 Seiten (143 ms bei 200) im Browser → Schreibansicht im DOM, Vorschau entprellt im Worker (Entscheidung #3).
2. **Vorlagenänderungen setzen alles neu** (Set-/Show-Regeln stehen in jeder Stilkette; Farbe kostet so viel wie Schriftgröße). → Schreibansicht zeigt Änderungen sofort per CSS, Vorschau folgt mit Hinweis.
3. **Wasm kostet gegenüber nativ (1 Thread) etwa Faktor 1,2–1,8**, beim Kaltstart mehr. Für Planung: Browserwerte nehmen.
4. **Speicher:** `evict(1)` drittelt den Speicher (947 → 292 MB bei 100 Seiten) ohne spürbaren Zeitverlust → übernommen, zusammen mit dem Überspringen unveränderter Eingaben.
5. **Worker-Größe ist das größte Startproblem.** Schriften auslagern und Code-Größe optimieren (M2/M3).
6. **SVG vs. Raster:** SVG ist im Browser schneller (25 vs. 52 ms) und skaliert verlustfrei → Vorschau mit SVG; Raster-Export ist entbehrlich, falls er sonst nicht gebraucht wird.

Kopfzeile mit `query` und „Seite x / y“ (zweiter Introspektionslauf) kosten nativ kaum etwas (Vergleich ohne Kopf-/Fußzeile: gleiche Größenordnung).
